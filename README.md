# memory-harness

A centralized, MCP-based long-term memory server. One OAuth-protected `/mcp` endpoint that any MCP client — Claude Desktop, Claude Code, Cursor, Windsurf, Cline, etc. — can connect to and read/write a shared markdown memory vault against. The harness itself has no AI or agent logic; it's purely storage + auth, exposed as MCP tools.

## How it works

1. An MCP client connects to `POST /mcp` and authenticates via OAuth (better-auth's `mcp` plugin: dynamic client registration, `/sign-in` for login, `/consent` for the authorization screen).
2. On each authenticated request, the server resolves the caller's display name, scaffolds the memory vault (`.mh/memories`) under the server's working directory if it doesn't exist yet, and starts an MCP session with instructions built from the vault's own `_meta.md`.
3. The connected client reads and writes markdown files in the vault through the registered tools below.

The vault is a single shared tree on disk (not per-user) — this is built for one person's own memory shared across their own set of clients, not multi-tenant isolation.

## MCP tools

Registered in [src/routes/mcp/index.ts](src/routes/mcp/index.ts), all path-based relative to the vault root:

- `memory_write` — create or overwrite a file, creating parent directories as needed
- `memory_append` — append to an existing file
- `memory_read` — read a file's full content
- `memory_list` — list files/directories under a path (optionally recursive)
- `memory_str_replace` — replace one exact, unique occurrence of a string in a file

`memory_search` and `memory_delete` are not implemented yet.

## Vault structure

Generated by [generateDefaultMemoryTree](src/lib/memory/default-memories-tree.ts) the first time the server runs:

```
.mh/memories/
├── _meta.md          entry point — read first, documents conventions
├── you/
│   ├── preferences.md   fixed file, no siblings
│   └── profile.md       fixed file, no siblings
├── topics/           one file per subject-matter thread
├── areas/            one file per ongoing responsibility/project
├── people/           one file per person
└── sessions/         dated pointers to past sessions, never full transcripts
```

Every folder has its own `_meta.md` with folder-specific conventions. Files are slugified markdown with `name` / `description` / `sources` / `aliases` (/ `status`) frontmatter.

## Getting started

```bash
pnpm install
cp .env.example .env   # fill in SERVER_URL, DB_FILE_NAME, BETTER_AUTH_SECRET, ALLOWED_HOSTS
pnpm db:push
pnpm dev
```

Then point an MCP client at `http://<SERVER_URL>/mcp`.

## Stack

- [TanStack Start](https://tanstack.com/start) — file-based server routes ([src/routes](src/routes))
- [better-auth](https://better-auth.com) with `@better-auth/mcp` and `@better-auth/oauth-provider` — OAuth/auth for MCP clients
- [`@modelcontextprotocol/sdk`](https://github.com/modelcontextprotocol/typescript-sdk) — `McpServer` + streamable HTTP transport
- Drizzle ORM over SQLite ([src/lib/db](src/lib/db))

## Scripts

```bash
pnpm dev            # start dev server
pnpm build           # production build
pnpm lint / format / check
pnpm db:generate / db:migrate / db:push / db:pull / db:studio
```

## Known gaps

- No per-user vault isolation — single shared tree per deployment.
- `you/preferences.md` / `you/profile.md` "fixed, no siblings" rule is only in the instructions text, not enforced by `memory_write`.
- `src/lib/memory/templates.ts` is currently unused dead code.
